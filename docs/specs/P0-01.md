## Objective / Dependencies

ให้ทุกบทบาทมีหน้าที่ ขอบเขต และผู้ตัดสินใจที่ตรวจสอบย้อนหลังได้ ตาม Task List §3.2 P0-01 และ Operating Model §1–§5, §9 ไม่มี task ก่อนหน้า แต่การปิดงานต้องมีผู้รับบทบาทธุรกิจยืนยัน RACI และมี commit ที่อ้างอิงได้

อ่าน AGENTS.md, WORKFLOW_STATE.json, RESUME.md, DECISIONS.md และเอกสารใน docs ทั้ง Task List v1.0, PRD v1.7, SDD v1.6, Operating Model v1.0 แล้ว อ้างอิงหน้าที่ธุรกิจจาก PRD §5, §16 และขอบเขตเทคนิคจาก SDD §4–§6, §13–§14

## In scope / Out of scope

ในขอบเขต: Task Contract, การกำหนดบทบาท Agent, RACI, reviewer, วิธีบันทึกอนุมัติ และ state/handoff ของ P0-01

นอกขอบเขต: สร้าง Git repository/โครงสร้างแอป (P0-02), Git policy/branch protection (P0-03), dependencies, schema, infra, UI, API และ business feature ทุกประเภท ไม่เปิด Phase ถัดไป

## RACI ที่เสนอให้ตรวจรับ

R = ผู้ทำ, A = ผู้รับผิดชอบตัดสินผลหนึ่งบทบาทต่อแถว, C = ผู้ให้ความเห็น, I = ผู้รับทราบ ทุก Agent ทำได้เฉพาะ task/allowed_paths ที่ lock แล้ว บทบาท Agent ไม่ใช่สิทธิ์ RBAC ของระบบจริง

| งาน/การตัดสินใจ | R | A | C | I |
|---|---|---|---|---|
| ยืนยันทีมและ RACI ของ P0-01 | master-agent | Product Owner | PM, คลัง, จัดซื้อ | Agent ทุกบทบาท |
| Scope, priority และ business acceptance | PM | Product Owner | คลัง, จัดซื้อ, การเงิน, master-agent | UX, FE, BE, DB, CI/CD, QA |
| Task lock, dependency, evidence และสถานะ | master-agent | master-agent | owner, reviewer, PM | Product Owner, ทีมที่เกี่ยวข้อง |
| Wireframe / UX baseline | ux-agent | PM | frontend-agent, qa-agent, ผู้แทนธุรกิจ | master-agent, backend-agent |
| Frontend delivery | frontend-agent | master-agent | ux-agent, backend-agent, qa-agent | PM |
| Backend / API contract | backend-agent | master-agent | frontend-agent, database-agent, qa-agent, security-reviewer | PM |
| Schema / migration / seed | database-agent | master-agent | backend-agent, cicd-agent, qa-agent | frontend-agent, PM |
| CI/CD / environment | cicd-agent | master-agent | frontend-agent, backend-agent, database-agent, qa-agent, security-reviewer | PM |
| Verification / defect evidence | qa-agent | master-agent | owner, ผู้แทนธุรกิจ | PM, Product Owner |
| Workflow คลังและ Opening Stock | ผู้แทนคลัง | PM | จัดซื้อ, การเงิน, QA, BE, DB | Product Owner, master-agent |
| Workflow จัดซื้อ | ผู้แทนจัดซื้อ | PM | คลัง, การเงิน, BE, QA | Product Owner, master-agent |
| Executive Phase Gate / Go-live | PM | Product Owner | ผู้แทนธุรกิจ, QA, master-agent | ทุกทีม |

RACI นี้กำกับงานโครงการเท่านั้น ไม่แทนผู้อนุมัติธุรกรรม: ผู้จัดการคลังยังเป็นผู้ยืนยัน Opening Stock และ PM ยังจัดการ approval policy รายโครงการตาม PRD

## Reviewer และช่องทางอนุมัติ

1. Master จัดเตรียม revision และ evidence ให้ตรวจใน task สนทนานี้ ผู้ใช้/เจ้าของโครงการเป็น reviewer ของ P0-01; การตรวจของผู้เขียนเองเป็น self-check ไม่ถือเป็น business approval
2. เสนอใช้ข้อความใน task สนทนานี้เป็นช่องทางอนุมัติ P0-01 โดยข้อความต้องระบุ Task ID, revision, ผู้รับบทบาท PO/PM/คลัง/จัดซื้อ และผล APPROVED หรือ CHANGES_REQUESTED ไม่ต้องใช้ชื่อบุคคลจริง
3. ตัวอย่างข้อความ: `อนุมัติ P0-01 revision 1; PO=...; PM=...; คลัง=...; จัดซื้อ=...; ยืนยัน RACI และใช้ task นี้เป็นช่องทางอนุมัติ`
4. Master บันทึกข้อความอ้างอิง ผู้อนุมัติ วันเวลา revision และผลใน DECISIONS.md และ WORKFLOW_STATE.json ไม่ถือความเงียบเป็นอนุมัติ
5. การอนุมัติธุรกิจ/Phase Gate ต้องมาจากมนุษย์ผู้มีอำนาจตาม Operating Model §1; Master ตรวจ technical evidence และเปลี่ยนสถานะหลังผ่านครบ การแก้ API/schema/permission/environment ในอนาคตต้องทำ Change Request ตาม Operating Model §3
6. ผู้ใช้/เจ้าของโครงการอนุมัติ revision 1 และยืนยันใช้ task สนทนานี้เป็นช่องทางอนุมัติเมื่อ 2026-09-24 ตาม D-011 ส่วน PR workflow และ branch policy ให้กำหนดใน P0-03
