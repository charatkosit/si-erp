# เอกสารความต้องการผลิตภัณฑ์ (PRD)

## ระบบบริหารคลังสินค้าและวัสดุโครงการสำหรับบริษัท System Integrator

**เวอร์ชัน:** 1.7 (เพิ่มรูปสินค้าใน Item Master)  
**วันที่:** 24 กันยายน 2569  
**ผู้ใช้งานหลัก:** ฝ่ายโครงการ, จัดซื้อ, คลังสินค้า, การเงิน, ผู้บริหาร และช่างติดตั้ง

---

## 1. ภาพรวม

บริษัทรับติดตั้งระบบ เช่น CCTV, Data Network, Access Point, IP Phone, MATV และ Access Control ต้องบริหารสินค้าโครงการที่มีทั้งอุปกรณ์ราคาสูง อุปกรณ์ประกอบ (accessories) และสินค้าที่ต้องติดตาม Serial Number/MAC Address อย่างเคร่งครัด

แต่ละโครงการมี BOQ ตั้งต้น แต่การจัดซื้อและส่งมอบงานเกิดเป็นหลายงวดตามแผนก่อสร้างและ Lead Time ของสินค้า บางรายการสั่งซื้อแล้วแต่ยังฝากเก็บไว้กับ Supplier (Supplier-held stock) จนกว่าจะเรียกส่งเข้าคลังหรือหน้างาน ระบบนี้จึงต้องเชื่อมข้อมูลตั้งแต่ BOQ → แผนจัดซื้อ → PO → สถานะสินค้า → รับเข้า → จัดของ → จ่ายออก/ติดตั้ง เพื่อให้เห็นความพร้อมของวัสดุและเงินทุนที่ผูกอยู่กับทุกโครงการแบบทันเวลา

เพื่อช่วยให้ผู้จัดสินค้า พนักงานส่งสินค้า และทีมติดตั้งระบุวัสดุได้ถูกต้อง ระบบต้องเก็บรูปอ้างอิงของสินค้าใน Item Master และแสดงรูปเดียวกันในงานรับเข้า จัดของ จ่าย และส่งมอบ

ระบบเป็น Web Application แบบ Responsive ใช้งานได้ทั้ง Desktop, Tablet และ Mobile โดย Mobile เน้นการสแกน Barcode/QR Code, รับสินค้า, ตรวจนับ และจ่ายสินค้า ณ คลังหรือหน้างาน

---

## 2. ปัญหาที่ต้องแก้

1. ไม่เห็นภาพรวมว่า BOQ โครงการใดสั่งซื้อแล้วเท่าไร ขาดเท่าไร และต้องใช้ทุนเพิ่มเท่าไร
2. สินค้าถูกสั่งหรือรับเข้าหลายงวด ทำให้มีโอกาสลืมสั่ง หรือสั่งเกินความต้องการ
3. ไม่ทราบว่าสินค้าที่สั่งแล้วอยู่ที่ Supplier, ระหว่างขนส่ง, คลังใด, หรือถูกจ่ายไปหน้างานแล้ว
4. การจัดของโครงการอาจไม่ครบ หาอุปกรณ์ไม่พบ หรือใช้สินค้าผิดโครงการ
5. อุปกรณ์ที่มี Serial/MAC และมูลค่าสูงต้องการประวัติรับเข้า-จ่ายออก-ติดตั้งที่ตรวจสอบย้อนหลังได้
6. ผู้บริหารต้องการคุม Cash Flow จากยอด BOQ, ยอดสั่งซื้อ, ยอดรับสินค้า และภาระซื้อคงค้างตามโครงการ

---

## 3. เป้าหมายและตัวชี้วัดความสำเร็จ

### เป้าหมาย

- ทำให้ทุก BOQ มีสถานะความครบถ้วนของการจัดหาและความพร้อมสำหรับติดตั้ง
- ควบคุมสินค้าคงเหลือแยกตามคลัง/พื้นที่เก็บ/สถานะ/โครงการ และตาม Serial Number เมื่อจำเป็น
- ทำให้การเตรียมวัสดุและจ่ายสินค้าโครงการตรวจได้ครบก่อนออกจากคลัง
- ทำให้ผู้บริหารเห็นเงินทุนที่ใช้แล้ว เงินทุนที่ต้องใช้เพิ่ม และสินค้า PO ที่ยังไม่เข้าบริษัท
- ทำให้ผู้บริหารเห็นมูลค่าสินค้าคงเหลือในคลัง แยกตามคลัง สถานะ และตำแหน่งเก็บ โดยอ้างอิงราคาซื้อจริงของ Lot ที่เหลือ

### KPI ระยะแรก

| ตัวชี้วัด | เป้าหมาย |
|---|---:|
| BOQ ที่แสดงสถานะจัดหาได้ครบถ้วน | 100% ของโครงการที่เปิดใช้ระบบ |
| รายการ Serial ที่ตรวจสอบเส้นทางย้อนหลังได้ | 100% ของรายการที่บังคับ Serial |
| ความคลาดเคลื่อนจากการตรวจนับ | ไม่เกิน 1% ของมูลค่าสต็อก |
| การจ่ายของที่มีใบจัดของ/ผู้อนุมัติ | 100% |
| รายงานทุนโครงการและ PO คงค้าง | ดูได้ตามเวลาจริงจากข้อมูลในระบบ |

## 4. ขอบเขตผลิตภัณฑ์

### ในขอบเขต (MVP)

- จัดการสินค้า, หมวดสินค้า, หน่วยนับ, ยี่ห้อ, รุ่น, Serial/MAC, Barcode/QR และรูปสินค้าอ้างอิง
- รับสต็อกตั้งต้น (Opening Stock) จากสินค้าคงค้างเดิม พร้อมตรวจนับ, ตรวจ Serial และอนุมัติผลต่างก่อน Go-live
- จัดการหลายคลัง หลายโซน หลายชั้นวาง หลายชั้น (Shelf) และช่องเก็บ (Bin) พร้อมระบุตำแหน่งของสินค้า/Serial แต่ละรายการ และแยกพื้นที่สินค้าราคาสูง/Accessories
- โครงการและ BOQ แบบหลายงวด
- แผนจัดซื้อ, PR/PO, สินค้ารอรับ, สินค้าฝาก Supplier, และสถานะระหว่างขนส่ง
- รับสินค้า, ตรวจ Serial, ย้ายที่เก็บ, จอง/จัดของ, จ่ายไปหน้างาน, รับคืน, ปรับสต็อก และตรวจนับ
- จัดการสินค้าตัวอย่างของบุคคลภายนอก, สินค้าฝากเคลม (RMA) และสินค้าไม่พร้อมขาย/กล่องไม่สมบูรณ์ โดยแยกจากสต็อกพร้อมจ่าย
- ติดตามต้นทุนโครงการ, มูลค่า PO, ภาระซื้อคงค้าง และสถานะความพร้อมวัสดุ
- คำนวณมูลค่าสินค้าคงเหลือเพื่อการบริหารจากราคาซื้อจริงแบบ FIFO โดยไม่ทำ GL หรือบัญชีเจ้าหนี้เต็มรูปแบบ
- สิทธิ์ผู้ใช้หลายระดับ พร้อม Audit Log
- Dashboard และรายงานส่งออก Excel/PDF

### นอกขอบเขตระยะแรก

- บัญชีเจ้าหนี้/GL เต็มรูปแบบ และการชำระเงินจริง
- ระบบจัดซื้อเชิงพาณิชย์ครบวงจร เช่น RFQ เปรียบเทียบราคา/อนุมัติหลายชั้นแบบซับซ้อน
- วางแผนทรัพยากรช่างและตารางโครงการแบบละเอียด
- เชื่อม ERP/Accounting/Supplier portal จริง (ออกแบบ API ไว้รองรับในระยะถัดไป)

## 7. กระบวนการทำงานหลัก

### 7.0 เตรียมและรับสต็อกตั้งต้นก่อน Go-live (Phase 0)

ระบบต้องรองรับสินค้าคงค้างเดิมที่ยังไม่รู้ว่าจะใช้กับโครงการใด โดยให้ถือเป็น **Shared Stock** ของบริษัท ไม่ผูกโครงการ จนกว่าจะถูกจองหรือจ่ายให้โครงการในภายหลัง

1. ผู้ดูแลระบบกำหนดวัน Cutover และสร้าง Opening Stock Batch สำหรับคลังทั้ง 5 แห่ง
2. ก่อนเริ่มนับ ต้องจัดทำ/ตรวจสอบ Item Master, หมวดสินค้า, หน่วยนับ, Location และนโยบาย Serial ให้ครบ
3. เจ้าหน้าที่คลังตรวจนับสินค้าจริงตามคลังและ Location; อุปกรณ์ที่ต้องเสียบไฟฟ้าต้องสแกน Serial/MAC ส่วน Accessories ให้บันทึกจำนวนและสภาพสินค้า
4. ของที่ไม่ทราบรหัส, Serial ไม่ชัดเจน หรือสภาพไม่พร้อมใช้งาน ต้องบันทึกเป็น `Quarantine` และไม่นำมาคำนวณยอดพร้อมใช้หรือยอดจัดซื้อ
5. ระบบบันทึก Opening Stock ผ่านเอกสารเฉพาะ ไม่ใช่ GRN หรือ PO ใหม่ เพื่อให้ตรวจสอบได้ว่าเป็นสินค้าคงค้างก่อนเริ่มระบบ
6. ผู้จัดการคลังตรวจสอบผลต่างและลงนามยืนยัน batch ก่อน Post; เมื่อ Post แล้ว ระบบเพิ่มยอด `Available – Shared Stock` และสร้างประวัติการเคลื่อนไหว `OPENING_BALANCE`
7. หลัง Go-live จัดซื้อจะเห็นเฉพาะยอดคงเหลือที่ผ่านการยืนยันแล้ว และสร้าง PR/PO เฉพาะปริมาณขาดหลังหัก Shared Stock ที่พร้อมใช้, ยอดจอง, และยอดสั่งซื้อที่ยืนยันแล้ว

### 7.1 ตั้งโครงการและ BOQ

1. PM สร้างโครงการ ระบุลูกค้า สถานที่ หน่วยงานรับผิดชอบ วันเริ่ม/จบ งบประมาณ และงวดงาน
2. PM นำเข้า BOQ จาก Excel หรือเพิ่มรายการด้วยตนเอง โดยระบุสินค้า ปริมาณ งวดใช้งาน และวันที่ต้องใช้ (Need-by date)
3. ระบบคำนวณต่อรายการ: ปริมาณ BOQ, สต็อกที่ใช้ได้, ปริมาณจองแล้ว, PO ที่ยืนยัน, Supplier-held, ระหว่างขนส่ง, รับเข้าจริง และปริมาณขาด
4. ระบบแสดงสถานะ `พร้อม`, `เสี่ยง`, `ขาด`, `เกิน` ตามวันต้องใช้และ Lead Time

### 7.2 วางแผนและสั่งซื้อหลายงวด

1. PM สร้าง Material Requirement ของแต่ละงวดจาก BOQ
2. ระบบเสนอปริมาณจัดซื้อโดยหักสต็อกว่างและ PO ที่ผูกกับโครงการแล้ว
3. จัดซื้อสร้าง PR/PO พร้อม Supplier, ราคาต่อหน่วย, ETA, เงื่อนไขการส่ง และสถานะการฝากเก็บ
4. PO แต่ละรายการต้องผูกกับโครงการ/BOQ line ได้มากกว่าหนึ่งรายการ และรองรับการรับสินค้าบางส่วน
5. สินค้าขนาดใหญ่ที่ยังอยู่ Supplier ให้บันทึกสถานะ `Supplier-held` พร้อมจำนวน พื้นที่เก็บของ Supplier, วันที่พร้อมเรียกส่ง และหลักฐานอ้างอิง

### 7.3 รับสินค้าและเก็บเข้าคลัง

1. เจ้าหน้าที่คลังเลือก PO/ใบส่งสินค้า หรือสร้างรับเข้ากรณีรับคืน/รับโอนที่ได้รับอนุมัติ
2. ตรวจจำนวน สภาพสินค้า และบันทึกใบรับสินค้า (GRN)
3. สำหรับสินค้า Serial-controlled ต้องสแกนหรือกรอก Serial Number; สินค้าที่เกี่ยวข้องให้บันทึก MAC Address, Warranty start/end และรูปฉลากได้
4. ระบบห้ามรับ Serial ซ้ำ และห้ามจ่าย Serial ที่สถานะไม่พร้อมใช้งาน
5. ทำ Put-away ไปยังตำแหน่งละเอียด `คลัง → โซน → Rack/ชั้นวาง → Shelf/ชั้น → Bin/ช่องเก็บ` โดยกำหนดพื้นที่ High-value และ Accessories แยกกัน และติดฉลาก QR/Barcode ให้ทุก Bin
6. สถานะสินค้าหลังรับเข้า: `พร้อมใช้`, `กักกัน/รอตรวจ`, `เสียหาย`, หรือ `รอจัดเก็บ`

### 7.4 จอง จัด และจ่ายของโครงการ

1. PM ส่งคำขอเบิกตามงวดงาน เลือกวันที่ต้องการใช้และสถานที่หน้างาน
2. ระบบตรวจความครบของ BOQ และสต็อกก่อนสร้างใบจัดของ (Pick List)
3. คลังจัดสินค้าโดยระบบสร้าง Pick List เรียงตามตำแหน่งเก็บ และสแกน Bin/Barcode/Serial เพื่อเปรียบเทียบกับใบจัดของแบบทันที
4. ใบจ่ายสินค้า (Issue Note) ต้องมีผู้ขอ ผู้อนุมัติ ผู้จัดของ ผู้รับของ และการยืนยันรับของ
5. เมื่อจัดของครบหรือได้รับอนุมัติให้ส่งบางส่วน คลังสร้างงานจัดส่งจากใบจัดสินค้า ระบุหน้างาน ผู้รับคาดหมาย พนักงานส่งสินค้า รถ และเวลานัดหมาย
6. พนักงานส่งสินค้าใช้มือถือยืนยันรับสินค้าออกจากคลัง โดยสแกนใบจัดสินค้า/Barcode ที่จำเป็น สถานะงานเปลี่ยนเป็น `กำลังจัดส่ง`
7. ที่หน้างาน ผู้รับลงนามในใบส่งของกระดาษ พนักงานส่งสินค้าบันทึกชื่อผู้รับ เวลา รูปถ่ายใบส่งของที่ลงนาม และสถานะ `ส่งมอบแล้ว`; หากส่งไม่ครบหรือถูกปฏิเสธ ต้องระบุจำนวน/เหตุผลและแนบรูปหลักฐาน
8. พนักงานส่งสินค้านำใบส่งของฉบับจริงกลับบริษัท เจ้าหน้าที่คลังบันทึก `รับเอกสารคืนแล้ว` พร้อมตรวจความครบถ้วนก่อนปิดงานจัดส่ง
9. ช่างหรือหัวหน้าทีมใช้มือถือยืนยันรับที่หน้างาน และเลือกสถานะ `รับหน้างาน`, `ติดตั้งแล้ว`, `เหลือรอใช้`, `คืนคลัง`, หรือ `เสียหาย`
10. ระบบห้ามปิดใบจ่ายเป็น “ครบ” หากรายการหรือ Serial ที่ต้องจ่ายยังไม่ครบ ยกเว้นมีผู้อนุมัติบันทึกเหตุผล

### 7.5 รับคืน ย้าย และตรวจนับ

- รับคืนจากหน้างานต้องตรวจ Serial/สภาพ และกำหนดว่าสามารถนำกลับใช้, ซ่อม, หรือจำหน่ายออก
- การย้ายระหว่างคลัง/Location ใช้ใบโอนและการยืนยันต้นทาง-ปลายทาง
- Cycle Count รองรับตรวจเฉพาะโซน/หมวด/สินค้าราคาสูง และใช้การสแกนบนมือถือ
- การปรับยอดหรือเปลี่ยนสถานะสินค้าต้องระบุเหตุผล หลักฐาน และผ่านผู้อนุมัติที่ไม่ใช่ผู้บันทึกรายการ

### 7.6 สินค้าตัวอย่าง, สินค้าฝากเคลม และสินค้าไม่พร้อมขาย

1. ระบบบันทึกข้อมูลสินค้า 3 มิติแยกกัน ได้แก่ `Ownership` (เจ้าของ), `Inventory Status` (สถานะสต็อก) และ `Physical Location` (ตำแหน่งเก็บ) เพื่อป้องกันสินค้าที่อยู่ในคลังจริงถูกนำไปจ่ายผิด
2. **สินค้าตัวอย่าง** รับผ่านเอกสารรับฝาก/รับตัวอย่าง ไม่ใช่ GRN หรือ Opening Stock ของบริษัท ระบุเจ้าของ, Supplier, Serial, วันที่รับ, กำหนดคืน และเก็บใน Zone/Bin `DEMO`; การนำออกใช้สาธิตใช้ใบยืม/คืนเท่านั้น
3. **สินค้าฝากเคลม** สร้างเลข RMA ผูกกับ Serial, GRN/PO เดิม, Supplier, อาการเสีย, รูปหลักฐาน และสถานะ `รอส่งเคลม → อยู่กับ Supplier → ซ่อม/เปลี่ยนใหม่/คืนเงิน → ปิดเคลม`; ก่อนส่งเก็บใน Bin `RMA`, หลังส่งเปลี่ยนตำแหน่งเป็น `External – Supplier RMA`
4. **สินค้าไม่พร้อมขาย/กล่องไม่สมบูรณ์** รับหรือย้ายเข้า Bin `HOLD`/`OPEN_BOX` พร้อมรูปและเหตุผล; ผู้จัดการคลังเลือกผลตรวจเป็น `แพ็กใหม่`, `ใช้ภายใน`, `ใช้ในโครงการโดย PM อนุมัติ`, `ขายลดราคา`, `เคลม`, หรือ `จำหน่ายทิ้ง`
5. สต็อกพิเศษทุกประเภทต้องถูกตัดออกจากยอด `Available` และยอดเสนอจัดซื้อโดยอัตโนมัติ จนกว่าจะมีการอนุมัติปลดสถานะตาม workflow

## 8. ความต้องการเชิงหน้าจอและประสบการณ์ใช้งาน

### Desktop

- หน้าจอ Dashboard แบบการ์ดสรุป ตารางเจาะลึก และกราฟแนวโน้มเงินทุน/ความพร้อมโครงการ
- หน้ารายการใช้ตัวกรองหลายเงื่อนไข, ค้นหาด้วยชื่อ/รหัส/Serial/MAC/PO/โครงการ และส่งออก Excel

- หน้าสินค้าหรือ Serial ต้องแสดงรูปสินค้าหลัก, ยอดแยกตาม Location และเส้นทางตำแหน่งเต็ม เช่น `WH-01 / HV / R03 / S02 / B04` พร้อมปุ่มเปิด Pick List ของตำแหน่งนั้น

### Mobile

- เมนูแบบ Bottom Navigation: งานของฉัน, สแกน, รับเข้า, จ่ายสินค้า, เพิ่มเติม
- ปุ่มสแกน Barcode/QR เด่นชัดและใช้งานด้วยกล้องโทรศัพท์
- รองรับสแกน QR/Barcode ของ Bin เพื่อยืนยัน Put-away, ย้ายสินค้า และ Pick จากชั้นที่ถูกต้อง
- ฟอร์มสั้น ใช้สถานะ/ปุ่มยืนยันแทนการกรอกข้อความยาว และรองรับอัปโหลดรูปหลักฐาน
- หน้าของพนักงานส่งสินค้าแสดงงานที่ได้รับมอบหมายตามลำดับนัดหมาย พร้อมข้อมูลหน้างาน, ผู้ติดต่อ, รายการส่งพร้อมรูปสินค้า, สถานะรับขึ้นรถ/กำลังจัดส่ง/ส่งมอบแล้ว/คืนเอกสารแล้ว และปุ่มถ่ายรูปใบส่งของที่ลงนาม
- หน้ารับสินค้า, Pick, จ่ายสินค้า และหน้าหน้างานแสดงรูปสินค้าหลักขนาดอ่านง่าย; หากยังไม่มีรูป ให้แสดงสัญลักษณ์ `ไม่มีรูปสินค้า` โดยไม่ขัดขวางการทำธุรกรรม
- หากสัญญาณไม่เสถียร ให้บันทึกร่างรายการในเครื่องและแจ้งรายการที่รอส่ง (รายละเอียด Offline-first พิจารณาใน Phase 2)

## 9. กฎธุรกิจสำคัญ

1. สินค้ามีรหัสสินค้า (SKU) เดียว แต่สามารถกำหนดได้ว่า `ไม่ติด Serial`, `บังคับ Serial`, หรือ `เลือกติด Serial ตามมูลค่า/รุ่น`
2. Serial Number ต้องไม่ซ้ำในระบบ และมีสถานะเพียงหนึ่งสถานะ/ตำแหน่ง ณ เวลาเดียวกัน
3. ปริมาณที่พร้อมนำไปหักความต้องการจัดซื้อ คือ `On-hand ที่พร้อมใช้ - จองให้โครงการอื่น + PO ยืนยันที่ยังไม่รับ + Supplier-held ที่ยืนยัน`
4. การจองสต็อกไม่ใช่การจ่ายจริง จึงต้องแสดงทั้งยอด Available และยอด Reserved อย่างชัดเจน
5. PO รับเข้าได้บางส่วน; ปริมาณที่เหลือจะยังคงเป็น Open PO จนกว่าจะปิดหรือยกเลิกอย่างมีสิทธิ์
6. สินค้า Supplier-held เป็น “สินค้าที่สั่งแล้วแต่ยังไม่เป็น On-hand ของบริษัท” โดยยังถือเป็นภาระ PO และเริ่มนับเป็นทรัพย์สินของบริษัทตั้งแต่ออกคำสั่งซื้อไปยัง Supplier ต้องไม่ถูกนำไปรวมกับสต็อกพร้อมจ่าย
7. อุปกรณ์ที่ต้องเสียบไฟฟ้าให้ถือเป็นสินค้าราคาสูง บังคับเก็บ Serial และกำหนด High-value location เมื่อเข้าคลัง การโยกสต็อกข้ามโครงการของกลุ่มนี้ต้องได้รับอนุมัติจาก PM
8. อุปกรณ์ประกอบ เช่น ท่อ, สาย Patch Cord และน็อต สามารถโยกสต็อกข้ามโครงการได้โดยเจ้าหน้าที่จัดสินค้า หรือผู้ดูแลคลังที่มีสิทธิ์ พร้อมบันทึกเหตุผลและประวัติการโยก
9. การแก้ไข BOQ หลังมี PO/รับเข้า/จ่ายแล้ว ต้องเก็บ Revision และแสดงผลกระทบต่อแผนจัดหา
10. ทุกการเคลื่อนไหวต้องมีเลขอ้างอิง ผู้ทำรายการ เวลา ต้นทาง ปลายทาง โครงการ (ถ้ามี) และเหตุผล
11. การลบเอกสารธุรกรรมต้องใช้การยกเลิก (Void/Cancel) ไม่ลบข้อมูลประวัติจริง
12. งานจัดส่งจะแยกจากใบจ่ายสินค้า แต่ต้องอ้างอิงใบจัดสินค้า/ใบจ่ายเดิมเสมอ; งานจะปิดสมบูรณ์ต่อเมื่อสินค้าส่งมอบครบหรือมีเหตุผลส่งไม่ครบที่ผ่านการยืนยัน และมีสถานะใบส่งของฉบับจริงกลับคืนบริษัท
13. Opening Stock ที่ผ่านการ Post มีสถานะเป็น Shared Stock และไม่ถูกนับเป็นการซื้อใหม่หรือ GRN ของโครงการ; การแก้ไขหลัง Post ต้องทำผ่าน Adjustment พร้อมผู้อนุมัติและ Audit Log
14. การคำนวณยอดที่จะจัดซื้อต้องหักเฉพาะสต็อก `Available` ที่ไม่ถูกจองให้โครงการอื่น และยอด inbound ที่ยืนยันแล้ว; Supplier-held ต้องนับเพียงครั้งเดียว แม้เป็นส่วนหนึ่งของ PO
15. ทุก Bin ต้องมีรหัส Location เฉพาะและ QR/Barcode; สินค้าชนิดเดียวกันเก็บได้หลาย Bin โดยระบบแสดงยอดแยกตาม Bin และยอดรวมของคลัง
16. Serial asset ต้องบันทึก current Location ระดับ Bin เสมอเมื่ออยู่ในคลัง; การรับเข้า, Put-away, Pick, ย้าย, รับคืน และปรับสต็อกต้องมีต้นทาง/ปลายทางระดับ Bin ตามประเภทธุรกรรม
17. มูลค่าสินค้าคงเหลือเพื่อการบริหารคำนวณจาก `ราคาซื้อจริงของ Lot ที่รับเข้า × จำนวนคงเหลือของ Lot` โดยตัด Lot ที่รับเข้าก่อนออกก่อน (FIFO)
18. อุปกรณ์ที่มี Serial ให้ผูกต้นทุนกับ Serial/GRN ที่รับเข้า; สินค้าไม่ติด Serial ให้ผูกต้นทุนเป็น Lot แล้วตัดปริมาณแบบ FIFO เมื่อจ่าย, ส่ง, คืน หรือปรับลด
19. Opening Stock ต้องบันทึกต้นทุนต่อหน่วยของ Lot ตั้งต้นจากเอกสารซื้อเดิม; หากหาไม่ได้ ให้ผู้จัดการคลังบันทึกราคาประมาณพร้อมเหตุผลและติดสถานะ `Estimated Cost` ในรายงาน
20. Ownership ของสินค้าแยกเป็นอย่างน้อย `COMPANY` และ `THIRD_PARTY`; สินค้าตัวอย่างของ Supplier/บุคคลภายนอกเป็น `THIRD_PARTY` จึงไม่นับเป็นสต็อกหรือมูลค่าทรัพย์สินของบริษัท
21. สินค้าฝากเคลมและสินค้าไม่พร้อมขายเป็น `COMPANY` แต่มีสถานะ `RMA_CLAIM` หรือ `NON_SELLABLE/HOLD`; ไม่รวมใน Available quantity และแสดงมูลค่า FIFO แยกต่างหาก
22. ห้ามเก็บ DEMO, RMA และ HOLD/OPEN_BOX ปะปนกับ Bin พร้อมจ่าย; ทุกการเปลี่ยนสถานะหรือย้ายออกนอกบริษัทต้องมีเหตุผล หลักฐาน และ Audit Log
23. รูปสินค้าเป็นข้อมูลอ้างอิงระดับ SKU/รุ่นใน Item Master ไม่ใช่รูปของ Serial เฉพาะตัวหรือรูปหลักฐานรับ-ส่ง; สินค้าหนึ่งรายการมีรูปหลักได้หนึ่งรูปและรูปเพิ่มเติมได้ตามจำนวนที่ผู้ดูแลระบบกำหนด
24. ผู้มีสิทธิ์ดูสินค้าเห็นรูปสินค้าได้ในหน้ารายการ, รายละเอียดสินค้า, รับเข้า, Pick List, ใบจ่าย, งานจัดส่ง และหน้ารับหน้างาน; การเพิ่ม เปลี่ยนรูปหลัก จัดลำดับ หรือเอารูปออก จำกัดเฉพาะผู้ดูแลระบบและผู้จัดการคลังที่ได้รับสิทธิ์
25. การเปลี่ยนแปลงรูปสินค้าไม่กระทบยอดสต็อก ต้นทุน หรือ Serial แต่ต้องมี Audit Log; รูปที่ถูกเอาออกต้องไม่ทำให้รูปหลักของเอกสารประวัติถูกเปลี่ยนย้อนหลัง

## 11. Dashboard และรายงานที่ต้องมี

### Dashboard ผู้บริหาร

- มูลค่า BOQ, PO ออกแล้ว, รับเข้าแล้ว, Open PO, Supplier-held และยอดคาดว่าจะต้องใช้เพิ่ม แยกตามโครงการ
- โครงการที่มีรายการขาด/เสี่ยงไม่ทัน Need-by date
- มูลค่าสต็อกคงเหลือ แยก High-value, Accessories, Quarantine และคลัง
- มูลค่าสต็อกคงเหลือแบบ FIFO แยกตามคลัง, สถานะ, หมวดสินค้า และสินค้าที่ใช้ Estimated Cost
- ยอดและมูลค่าสต็อกพิเศษแยกเป็น DEMO (Third-party), RMA และ Non-sellable/Hold โดยไม่ปะปนกับ Available stock
- Top 10 สินค้าที่ขาดบ่อย, ค้างนาน, หรือมีมูลค่าสูง

### Dashboard PM

- BOQ readiness ต่อโครงการและต่องวดงาน
- รายการที่ต้องสั่งก่อนตาม Lead Time
- รายการรอรับจาก Supplier และรายการจัดของไม่ครบ
- สินค้าจ่ายไปหน้างานแต่ยังไม่ยืนยันติดตั้ง/คืน

### รายงานหลัก

1. รายงาน BOQ เทียบกับจัดซื้อ/รับเข้า/จ่ายออก/ขาด แยกตามโครงการและงวด
2. รายงาน Cash Flow วัสดุโครงการ: งบ BOQ, PO committed, รับเข้า, Open PO และประมาณการขาด
3. รายงาน Stock Card และประวัติ Serial/MAC แบบย้อนหลัง
4. รายงานสต็อกตามคลัง/Location/สถานะ/อายุสต็อก
5. รายงานสินค้า Supplier-held และกำหนดเรียกส่ง
6. รายงาน Pick/Issue ที่ค้างรับ ค้างยืนยัน หรือจ่ายไม่ครบ
7. รายงานผลตรวจนับและรายการปรับยอด
8. รายงานงานจัดส่งที่กำลังส่ง, ส่งมอบแล้วแต่ยังไม่คืนเอกสาร, ส่งไม่ครบ และสรุปหลักฐานรับสินค้า
9. รายงาน Opening Stock: ยอดตรวจนับ, รายการ Quarantine, ผลต่างก่อน Post และ Shared Stock ที่ยังไม่ผูกโครงการ
10. รายงานตำแหน่งสินค้า: สินค้า/Serial ตามคลัง–Rack–Shelf–Bin, Bin ว่าง, ยอดต่อ Bin และประวัติการย้ายตำแหน่ง
11. รายงานมูลค่าสต็อก: ยอดจำนวนและมูลค่า FIFO ของสินค้าในคลัง, Quarantine, Reserved, Estimated Cost และ Supplier-held (แยกรายงาน ไม่รวมมูลค่า On-hand)
12. รายงานสต็อกพิเศษ: สินค้าตัวอย่างใกล้ครบกำหนดคืน, RMA ค้างตาม Supplier/อายุเคลม, สินค้า Hold/Open-box และมูลค่าที่รอผลตรวจ

## 13. การแจ้งเตือน

- แจ้ง PM/จัดซื้อเมื่อรายการ BOQ ต่ำกว่าแผนหรือ ETA เกิน Need-by date
- แจ้งคลังเมื่อมีคำขอจัดของ/รับเข้า/โอนที่รอดำเนินการ
- แจ้งผู้อนุมัติเมื่อมี Adjustment, จ่ายสินค้าราคาสูง หรือจ่ายไม่ครบ
- แจ้ง PM เมื่อสินค้าจ่ายไปหน้างานแต่ยังไม่ยืนยันรับ/ติดตั้งตามเวลาที่กำหนด
- แจ้งพนักงานส่งสินค้าเมื่อได้รับมอบหมายงานจัดส่งหรือใกล้เวลานัดหมาย
- แจ้งคลังเมื่อส่งมอบแล้วแต่ใบส่งของฉบับจริงยังไม่ถูกบันทึกรับคืนภายในเวลาที่กำหนด
- แจ้งคลังเมื่อสินค้าตัวอย่างใกล้กำหนดคืน, RMA ค้างเกินกำหนด, หรือสินค้า HOLD/OPEN_BOX รอผลตรวจนานเกินเกณฑ์
- แจ้งผู้บริหารเมื่อมูลค่า Open PO หรือเงินทุนคาดการณ์เกินเกณฑ์ที่ตั้งไว้

## 14. ลำดับการพัฒนา

### Phase 0 — เตรียมข้อมูลและ Cutover สต็อกตั้งต้น

- ทำความสะอาด Item Master, Location, หน่วยนับ และนโยบาย Serial; รวบรวม/คัดเลือกรูปสินค้าหลักของ SKU สำคัญก่อน Go-live
- รวบรวมราคาซื้อเดิม/ต้นทุนตั้งต้นของสินค้าคงค้าง และระบุรายการที่ต้องใช้ Estimated Cost ก่อน Post Opening Stock
- สร้างและติดฉลาก QR/Barcode สำหรับ Rack, Shelf และ Bin ของทั้ง 5 คลัง ก่อนเริ่มตรวจนับ
- สร้าง Opening Stock Batch, นำเข้า/สแกน/ตรวจนับ, จัดการ Quarantine และรายงานผลต่าง
- อนุมัติและ Post `OPENING_BALANCE` สำหรับ 5 คลัง ก่อนเปิดธุรกรรมจริง

### Phase 1 — คลังและการติดตามโครงการพื้นฐาน

- Login/RBAC, สินค้าและรูปสินค้า, คลัง/Location, Supplier, โครงการ/BOQ
- PR/PO, Supplier-held, รับเข้า, Serial/MAC, สต็อก, จอง/จัด/จ่าย, งานจัดส่งหน้างาน และรับคืน
- สินค้าตัวอย่าง, RMA, HOLD/OPEN_BOX และรายงานสต็อกพิเศษ
- Dashboard BOQ readiness และรายงานพื้นฐาน

### Phase 2 — ควบคุมเงินทุนและการปฏิบัติการ Mobile

- รายงาน Cash Flow วัสดุ, แจ้งเตือน, Approval workflow
- Mobile scanner ที่สมบูรณ์, Cycle count, รูปหลักฐาน และ Offline draft
- Import/Export ขั้นสูง และ API สำหรับเชื่อมบัญชี/ERP

### Phase 3 — การวิเคราะห์และการเชื่อมต่อภายนอก

- Forecast การจัดซื้อจาก Lead Time และแผนติดตั้ง
- Supplier portal/EDI, การเชื่อม Accounting, BI dashboard และ SSO/MFA

## 15. เกณฑ์ยอมรับ (MVP Acceptance Criteria)

1. สร้างโครงการและนำเข้า BOQ ได้ พร้อมแบ่งงวดงานและวันที่ต้องใช้
2. ระบบแสดงยอด BOQ, สต็อกว่าง, ยอดจอง, PO, Supplier-held, รับเข้า และยอดขาดต่อรายการได้ถูกต้อง
3. PO หนึ่งใบรับสินค้าได้หลายงวด และติดตามยอดคงค้างได้
4. รับสินค้า Serial-controlled ด้วยการสแกน/กรอก Serial ได้ และระบบป้องกัน Serial ซ้ำ
5. ย้าย จอง จัด จ่าย และรับคืนสินค้าได้ โดยประวัติ Serial และ Stock Card ถูกต้อง
6. เจ้าหน้าที่ใช้มือถือสแกนสินค้าเพื่อรับเข้าและจ่ายสินค้าได้
7. PM เห็นรายการ BOQ ที่เสี่ยงหรือขาดก่อนวันใช้งานได้
8. ผู้บริหารเห็นยอด PO committed, Open PO, Supplier-held และยอดคาดการณ์เงินทุนของแต่ละโครงการได้
9. การปรับสต็อกและจ่ายสินค้าราคาสูงผ่านการอนุมัติตามสิทธิ์ พร้อม Audit Log
10. ผู้ใช้แต่ละบทบาทมองเห็นเฉพาะเมนูและข้อมูลที่มีสิทธิ์
11. พนักงานส่งสินค้ารับงานบนมือถือ ยืนยันรับของออกจากคลัง บันทึกการส่งมอบพร้อมรูปใบส่งของที่ลงนาม และคลังบันทึกรับเอกสารฉบับจริงคืนได้
12. สามารถรับสต็อกตั้งต้นสำหรับทั้ง 5 คลังได้ โดยแยก Serial/Quarantine ตรวจผลต่าง และ Post เป็น Shared Stock ได้หลังการอนุมัติ
13. สินค้าและ Serial ค้นหาตำแหน่งได้ถึงระดับ Bin; การ Put-away, ย้าย และ Pick ต้องยืนยัน Location ด้วยการเลือกหรือสแกน
14. ผู้บริหารดูมูลค่าสต็อก On-hand ได้ตาม Lot ต้นทุน FIFO และรายงานแสดงรายการ Estimated Cost แยกชัดเจน
15. สินค้าตัวอย่าง, RMA และสินค้าไม่พร้อมขายถูกแยกจาก Available stock, แสดงเจ้าของ/ตำแหน่ง/หลักฐาน และไม่ถูกนำไปเสนอจัดซื้อหรือจ่ายสินค้าโดยอัตโนมัติ
16. ผู้จัดสินค้า พนักงานส่งสินค้า และทีมติดตั้งเห็นรูปสินค้าหลักในรายการงานของตน; การเปลี่ยนรูปสินค้าอยู่ภายใต้สิทธิ์และทิ้ง Audit Log โดยไม่กระทบรายการรับ/จ่ายเดิม

## 16. ข้อยืนยันสำหรับการออกแบบเชิงเทคนิค

| หัวข้อ | ข้อยืนยัน |
|---|---|
| หลักการต้นทุน | ใช้ราคาซื้อจริงต่อ Lot และตัดจำนวนแบบ FIFO เพื่อแสดงมูลค่าสต็อก/ต้นทุนเพื่อการบริหารเท่านั้น ไม่สร้างรายการ GL หรือระบบบัญชีเจ้าหนี้เต็มรูปแบบ |
| Supplier-held | เป็นภาระ PO และเริ่มนับเป็นทรัพย์สินของบริษัทตั้งแต่ออกคำสั่งซื้อไปยัง Supplier แต่ไม่ใช่ On-hand stock จนกว่าจะรับเข้าคลัง/หน้างาน |
| สต็อกกลาง | ทุกโครงการใช้สต็อกกลางร่วมกันได้ โดยอุปกรณ์ที่ต้องเสียบไฟฟ้า/สินค้าราคาสูงต้องให้ PM อนุมัติก่อนโยกข้ามโครงการ |
| Accessories | ท่อ, สาย Patch Cord, น็อต และอุปกรณ์ประกอบ สามารถโอนข้ามโครงการได้โดยเจ้าหน้าที่จัดสินค้า หรือผู้ดูแลคลังตามสิทธิ์ |
| คลังสินค้า | มี 5 คลัง อยู่ในบริษัทเดียวกัน ไม่มีสาขา ระบบต้องรองรับการย้ายระหว่างคลังและระหว่าง Location ภายในคลัง |
| Serial | บังคับเก็บ Serial สำหรับสินค้าเป็นอุปกรณ์ที่ต้องเสียบไฟฟ้าเพื่อใช้งาน; MAC, Warranty และรูปฉลากให้เก็บเมื่อมีข้อมูล |
| ระบบบัญชีอนาคต | เปิด API/Integration layer สำหรับระบบบัญชีที่บริษัทพัฒนาเองในอนาคต โดยเริ่มจากการส่งออกข้อมูลที่มีเลขอ้างอิงเดียวกัน |
| Approval workflow | PM เป็นผู้จัดการลำดับอนุมัติของธุรกรรมในโครงการ ได้แก่ PR, PO, Issue และ Adjustment; ระบบต้องตั้งค่าได้รายโครงการ |
| Opening Stock | ต้องมีวัน Cutover, batch สำหรับตรวจนับ, สถานะ Draft/Counting/Review/Posted, และ Shared Stock ที่ไม่ผูกโครงการ; ผู้จัดการคลังเป็นผู้ยืนยันก่อน Post |
| Storage Location | ใช้รหัสมาตรฐาน `Warehouse / Zone / Rack / Shelf / Bin`; ทุก Bin ต้องติด QR/Barcode และเป็นหน่วยต่ำสุดของการเก็บ/ย้าย/นับสินค้า |
| Stock valuation | ราคาซื้อจริงของวันที่รับเข้าเป็นต้นทุนของ Lot/Serial; สินค้าออกตัด Lot แบบ FIFO และ Opening Stock ที่ไม่มีต้นทุนจริงต้องติด Estimated Cost |
| Special stock | ใช้ Ownership แยกจาก Inventory Status; DEMO เป็น Third-party ไม่รวมมูลค่าบริษัท, RMA/HOLD เป็นทรัพย์สินบริษัทที่แยกจาก Available และเก็บใน Bin เฉพาะ |
| รูปสินค้า | รูปสินค้าอยู่ใน Item Master ระดับ SKU/รุ่น มีรูปหลักหนึ่งรูปและรูปเพิ่มเติม; แสดงในงานปฏิบัติการทุกบทบาทที่มีสิทธิ์ดูสินค้า แต่จัดการรูปได้เฉพาะสิทธิ์ที่กำหนด และไม่ปะปนกับรูป Serial/หลักฐานธุรกรรม |

## 17. ผลลัพธ์ที่คาดหวัง

เมื่อใช้งาน ระบบจะช่วยให้บริษัททราบทันทีว่าแต่ละโครงการ “ต้องใช้อะไร, สั่งแล้วหรือยัง, ของอยู่ที่ไหน, ยังขาดอะไร, และต้องใช้เงินเพิ่มเท่าไร” พร้อมลดความผิดพลาดในการจัดของและทำให้สินค้าที่มี Serial/มูลค่าสูงตรวจสอบได้ตลอดวงจรชีวิต
